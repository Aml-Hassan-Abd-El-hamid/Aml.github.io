NLP and Clustering

Clustering bilingual texts -Arabic and English-

Aml Hassan Esmail Arabic and English CPU-first design

Currently, I’m working on building a desktop note-taking app, and I wanted to add a feature that can help the user to group similar notes automatically, so I started searching for the best way to group those notes, and I wanted to share my journey with you in this article.

I wanted an algorithm that could do the following:

  • Support two languages: Arabic and English
  • Works well in CPU, as most regular users don’t have a very good personal GPU

Also, to make it easier for me, I put a limit on the number of notes that can be grouped to a maximum of 1k notes.

Working Plan:

  • Settle on clustering algorithms to test.
  • Find/Build a test dataset
  • Settle on the embedding models to test.
  • Compare and choose the fastest and most accurate way.

The clustering algorithms:

When choosing the clustering algorithm, I needed one with the following criteria: fast, computationally inexpensive, doesn’t need specification of a number of clusters by the user, and has the least amount of hyperparameters that need to be tuned.

I decided to experiment with Louvain

Louvain’s time complexity is usually O(n log n), but since I need to calculate the similarity matrix before using it, and that step takes O(n²), the overall time complexity of the clustering process became O(n²).

The way it worked is that I calculated the embedding for each text, calculated the cosine similarity matrix for those embeddings, put those texts as nodes inside a graph and created edges between those nodes based on their cosine similarity, and then I used the Louvain algorithm over that graph.

This algorithm has a few hyperparameters that need to be tuned. For Louvain, there’s essentially one main parameter, which is the resolution parameter, it controls the size of communities.

Another hyperparameter that I had to set was the threshold, which decides if 2 texts are related or not based on their cosine similarity score; the relationship over here is represented as an edge between the 2 texts.

If you’re unfamiliar with Louvain, this video can be a great intro

Note: I experimented a little bit with DBSCAN at the start, but trying to set its hyperparameters automatically was a hellish experience; the most convenient thing about Louvain is the fact that setting its hyperparameters automatically was kinda easy which is really important given the fact that this feature will be run be a user who will probably know nothing about sitting clustering algorithms hyperparameters.

The test dataset

I built the dataset by:

  • Sampling 500 texts with 6 different labels from here Arabic News Articles Dataset, I made sure that all the categories got different random numbers of samples inside them: Politics: 94, Sports: 110, Finance: 83, Tech: 67, Religion: 66, Medical: 80.
    I also made sure the text lengths vary across the samples.
  • And sampling 500 texts with 6 different labels from here News Topics Classification Dataset, I made sure that all the categories got different random numbers of samples inside them: Politics: 50, Sport: 87, Business: 81, Tech: 55, Religion: 169, Entertainment: 58.
    I also made sure the text lengths vary across the samples
  • And then putting the English and Arabic texts that belong to the same category together -considered Business and Finance the same category- and left the Medical category to be only Arabic texts, and the Entertainment category to be only English texts

The test dataset can be found here: bilingual text clusters

The embedding models

Given the fact that the application that I’m building will be mostly dependent on CPU only, I had to choose the lightest models possible, and of course, the model needs to handle Arabic and English.

Evaluation metrics

For this project, I needed 2 types of evaluation metrics:

One set that was used to automatically choose the values of the hyperparameters for those algorithms, as the user won’t have enough knowledge to choose the values themselves. For that, I depended mainly on modularity, it was an easy choice given the fact that the Louvain algorithm is based on the idea of optimising the modularity measure.

Alongside modularity, I also considered the balance score, the largest community percentage of nodes, and the percentage of small communities. However, all those measures had much smaller weights compared to modularity; none of them is multiplied by any weight higher than 0.2 while modularity is multiplied by 1.

I also used filters on the communities sizes to help with automatically choosing the values of the hyperparameters. If a set of hyperparameters produced communities that got a very large size, for example, one community contains more than 70% of the points, that set of hyperparameters would be ignored. Also, if a set of hyperparameters produced too many small communities, for example, more than 50% of the communities got only 1 or 2 nodes, that set of hyperparameters would be ignored

The other set of metrics was used to evaluate the clustering process on the test dataset using the labels of the data, that set wouldn’t be available for the user, of course, given that the user won’t probably have the true labels of their clusters, and for that set I picked the following ones:

ARI: short for Adjusted Rand Index, measures the exact matching performance, meaning that in order for that to be 1, every pair of nodes that belong to the same true cluster must be in the same predicted cluster, and every pair of nodes that belong to different true clusters must be in different predicted clusters.

NMI: short for Normalised Mutual Information, measures the information shared between clusterings, meaning that in order for that to be 1, all the nodes in each true cluster must be assigned to the same predicted cluster, and each predicted cluster must contain only nodes from a single true cluster.

FMI: Short for Fowlkes-Mallows Index, handles precision/recall balance in uneven clusters.

Purity: ensures clusters contain mostly one class, that one can be deceiving alone, cause if you divide all the nodes into singleton clusters where each one have only one node, you’ll end up with purity =1, that’s why it’s important to use this metric as a side metric not the main one.

The final comparison

You can find the full code that I run to get those results over here: https://www.kaggle.com/code/amlhassan/clustering-arabic-and-english-texts-using-louvain

I made sure to use random seeds and to set the randomize flag from community_louvain.best_partition() to False, to make the results as reproducible as possible.

In the table above:

  • The total time includes the looping over different thresholds and resolution values to find the best ones given the metrics defined in the evaluation section above, while the embedding time, of course, is the time taken by the model to just produce the text embeddings.
  • The no.pure clusters is no.of clusters that got over 90% of it from only one class, while no.clusters is the total number of clusters produced by the algorithm.

I ran the whole code over Kaggle’s CPU, which has 2 cores, and Kaggle also has a RAM that’s around 32 GB.

Based on my comprehensive testing across four multilingual embedding models and the Louvain clustering algorithm, I found that the paraphrase-multilingual-mpnet-base-v2 model gave me the optimal balance of accuracy and performance. While this 1.1GB model isn’t the smallest option indeed 😑, it got the highest scores across most key metrics (ARI: 0.71, NMI: 0.76, FMI: 0.76, Purity: 0.85) and produced 7 clusters where 4 of them were over 90% pure.

For practical implementation in my note-taking application, this approach offers several advantages:

  • First, it accurately groups related content across both Arabic and English without requiring language detection as a preprocessing step.
  • Second, with an embedding time of just 174 seconds for 1,000 notes on a modest 2-core CPU, I think the time is not so bad, I think a user can wait around 2 and a half minutes to get a proper clustering of 1,000 nodes over their CPU!
  • Finally, the automatic hyperparameter selection process means users won’t need technical expertise to achieve high-quality clustering results.

Future improvements could include:

  • Testing the code on a RAM with less than 32GB of memory
  • Try Onnx, openVinew backend and quantisation to speed up the embedding part.
